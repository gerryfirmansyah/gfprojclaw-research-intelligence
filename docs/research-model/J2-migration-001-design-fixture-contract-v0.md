# J2 Migration 001 Design & Fixture Contract v0

Status: **J2 ACTIVE — Migration 001 Design & Fixture Contract**

## 1. Purpose

This document translates the accepted J2 Canonical DDL Contract into a **migration implementation contract** and a **small deterministic fixture contract** for the first executable PostgreSQL slice.

The goal is to make the next step implementation-ready without yet changing the production database.

The governing principle is:

> **Migration 001 must prove the canonical evidence-to-judgment path with minimal schema, deterministic fixtures, and reversible engineering behavior, while preserving scientific history and HUMAN authority.**

This document defines what Migration 001 must create, in what order, what it must not create, how fixtures are shaped, and how success is validated.

```text

research_project_version

source_record
```

No Theory, Method, Concept, ExistingSolution, Synthesis, R0–R16, scheduler/job, or add-in tables are introduced in Migration 001.

This is deliberate scope control, not a rejection of those objects.

## 5. Migration Execution Contract

Migration 001 should be executable as one logical migration.

Preferred behavior:

```text
BEGIN
  create required extension only if approved/needed
  create tables in dependency order
  add deferred circular/current-version foreign keys
  create indexes
  create check constraints
  validate static seed definitions if any
COMMIT
```

### Important constraint

Engineering transaction rollback is appropriate if the DDL migration itself fails.

This is **not** a global research gate. It is ordinary database atomicity for one engineering unit.

A failed migration must not be interpreted as a scientific failure.

---

## 6. UUID Generator Contract

Preferred implementation:

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;
```

only if:

- the deployment allows extension creation; and
- no approved UUID function already exists.

Then:

```sql
DEFAULT gen_random_uuid()
```

If `pgcrypto` already exists, Migration 001 must not depend on reinstallation.

If extension creation is operationally restricted, UUIDs may be generated by the application while preserving the `uuid` DDL contract.

The logical schema must not depend on domain-specific ID formats.

## 9. DDL Idempotency Policy

Migration 001 is a versioned migration, not a repeatedly executed bootstrap script.

Therefore the default contract is:

- migration runner records whether `001` has been applied;
- normal schema objects should **not** be silently skipped using broad `IF NOT EXISTS` everywhere;
- unexpected pre-existing canonical table names should be treated as an engineering conflict requiring inspection.

`IF NOT EXISTS` is acceptable for safe infrastructure prerequisites such as an already-approved extension.

### Why

Broad idempotency can hide schema drift.

The migration must prefer explicit state over silent partial application.

## 10. Fixture Purpose

The fixture exists to validate the canonical model and power early UI replacement.

It is **not** production scientific evidence.

Fixtures must be visibly synthetic/reference data.

The fixture must test both reference research profiles with the same schema and code path:

```text
Profile A — Computer / Information Systems
Profile B — Management / Organization Studies
```

This fixture is a generality test, not two separate domain implementations.

---

## 11. Fixture Safety Contract

Every fixture record must be distinguishable from production research data.

Recommended fixture conventions:

```text
created_by = 'FIXTURE_J2_001'
origin = 'FIXTURE'
source_key values prefixed with 'fixture_'
fixture labels include '[FIXTURE]' where user-visible
```

Synthetic Work metadata should not impersonate a real DOI or publication.

Recommended DOI policy:

```text
Do not assign DOI to synthetic fixture Works.
```

Use synthetic identifier types only where the current CHECK vocabulary safely permits `OTHER`.

---

## 12. Deterministic Fixture Identity Contract

Fixture IDs should be deterministic so verification and UI prototype integration can reference stable records.

Use explicitly assigned UUIDs in the fixture SQL rather than `gen_random_uuid()`.

Suggested namespace pattern:

```text
A objects: 10000000-0000-4000-8000-...
B objects: 20000000-0000-4000-8000-...
shared/source objects: 30000000-0000-4000-8000-...
```

Exact UUID values may be selected during implementation, but they must:

- be valid UUIDs;
- be unique;
- remain stable once committed;
- never encode sensitive information.

## 16. Fixture LiteratureSource Contract

Use one neutral synthetic provider:

```text
source_key = 'fixture_reference_source'
name = '[FIXTURE] Reference Literature Source'
source_type = 'REFERENCE_FIXTURE'
active = true
```

If `source_type` is constrained in final DDL, the fixture must use an allowed generic source type rather than introducing a domain-specific value.

Fixture source records must preserve the same provenance rules as real records.

---

## 17. Fixture Work Contract

Each profile gets two synthetic Works:

```text
Work 1: primarily supportive/relevant to the candidate gap
Work 2: challenging, contradictory, or partially addressing the gap
```

This is important because the first fixture must prove that the system can retain both supportive and counter-evidence.

The fixture must not create a one-sided evidence world.

Minimum access mix per profile should include at least:

```text
1 ABSTRACT_ONLY Work
1 FULL_TEXT Work
```

or, if text-rights handling is not yet implemented, two bounded synthetic fragments with explicit fixture access levels.

No METADATA_ONLY Work may produce a passage-level EvidenceFragment.

---

## 18. Fixture Evidence & Claim Contract

Each Work contributes one bounded EvidenceFragment and one atomic Claim.

Required invariant:

```text
1 EvidenceFragment → 1 fixture Claim
```

Each Claim has exactly one primary EvidenceFragment.

For each profile:

```text
Claim 1 SUPPORTS GapCandidate
Claim 2 CHALLENGES or ADDRESSES GapCandidate
```

This proves that contradictory/weakening evidence remains first-class.

At least one fixture relationship must not be `SUPPORTS`.

---

## 19. Fixture GapCandidate Contract

Each project gets one project-scoped `research_object_identity` with:

```text
object_type = 'GAP_CANDIDATE'
```

and one matching `gap_candidate` typed row sharing the same UUID.

Profile A and Profile B use the same typed structure.

Recommended initial evolution state:

```text
CONTESTED
```

or:

```text
CANDIDATE
```

The fixture should preferably use `CONTESTED` because it demonstrates that evidence can point in different directions.

Human acceptance must not be inferred from this state.

---

## 20. Fixture Assessment Contract

Each GapCandidate gets one Assessment with four first-slice dimensions:

```text
GAP_EVIDENCE_STRENGTH
COUNTER_EVIDENCE_RISK
EVIDENCE_COVERAGE_CONTEXT
REVIEW_PRIORITY
```

Values may be numeric advice values for UI testing, for example 0–100, but the fixture must label them as advice.

The fixture must not include:

```text
Q1 acceptance probability
truth probability
publication probability
scientific PASS/FAIL
```

The assessment explanation should mention both supporting and challenging evidence.

---

## 21. Fixture ChangeEvent Contract

Each project gets one meaningful ChangeEvent.

Example structure:

```text
change_type = 'EVIDENCE_BALANCE_CHANGED'
reasoning_delta = 'New challenging evidence makes the candidate gap contested.'
```

The event links to:

- one primary GapCandidate;
- one CoverageContext;
- current/previous bounded state snapshots where useful.

The fixture must not create ChangeEvents for raw ingestion events.

---

## 22. Fixture HumanDecision Contract

Each project gets one HumanDecision to prove HUMAN authority is independent from machine assessment.

Recommended fixture decision:

```text
NEED_MORE_EVIDENCE
```

with rationale such as:

```text
Supporting and challenging claims are both present; broader counter-search is needed before refining the research direction.
```

This decision must remain independent from the numeric AssessmentDimension values.

No score threshold generates the HumanDecision.

---

## 23. Fixture Coverage Contract

Each project gets one CoverageContext.

Profile A and B should deliberately use slightly different coverage conditions while preserving the same schema.

Example:

```text
Profile A:
- fixture source HEALTHY
- counter-search state PARTIAL

Profile B:
- fixture source DEGRADED or HEALTHY
- access mix differs
```

The goal is to prove that scientific interpretation can carry explicit coverage limitations without system blocking.

If a fixture uses `DEGRADED`, evidence already captured remains available and valid as fixture evidence.

---

## 24. Fixture Cross-Domain Generality Test

The fixture is accepted only if all of the following are true:

```text
Profile A inserts without schema changes.
Profile B inserts without schema changes.
No domain-specific table exists.
No domain-specific FK or CHECK constraint exists.
No migration branch tests the profile domain.
Both profiles traverse the same evidence chain.
Both profiles can produce Assessment, ChangeEvent, CoverageContext, and HumanDecision.
```

A difference in fixture vocabulary is expected.

A difference in core schema is not.

If a future fixture exposes a genuine difference, classify it as:

```text
PROFILE_CONFIG
CORE_GENERALIZATION
ADD_IN_CANDIDATE
UNRESOLVED_GENERALITY
```

and continue the project without a global lock.

---

## 25. Verification Script Contract

`001_vertical_slice_verify.sql` should be read-only and deterministic.

It must verify at least:

### Schema existence

All 21 expected tables exist.

### Profile/project identity

Exactly the expected fixture Profiles and Projects exist.

### Evidence chain integrity

For every fixture EvidenceRelationship, the query can traverse:

```text
GapCandidate
← EvidenceRelationship
← Claim
← EvidenceFragment
← Work
← WorkSourceRecord
← SourceRecord
← LiteratureSource
```

### Atomic claim rule

No fixture Claim has a null EvidenceFragment.

### Metadata-only rule

No EvidenceFragment has `METADATA_ONLY` access.

### Generic identity rule

Every fixture GapCandidate has matching `research_object_identity.object_type = GAP_CANDIDATE`.

### HUMAN separation

HumanDecision exists independently from Assessment.

### Coverage separation

CoverageContext exists and source health does not mutate existing evidence.

### Cross-domain generality

Both A and B pass the same verification query shape.

---

## 26. Verification Failure Semantics

Verification failures are engineering/integrity defects localized to the migration/fixture environment.

They do not mean:

```text
Profile A science failed
Profile B science failed
research project rejected
pipeline globally locked
```

The migration fixture environment should be corrected and rerun.

Scientific judgment remains outside schema verification.

---

## 27. Rollback Contract

Migration 001 must have a clear rollback strategy before production use.

Preferred development/test rollback:

```text
Drop the Migration 001 canonical tables in reverse dependency order
```

only in isolated development/test databases where no scientific history exists.

For production, once canonical scientific records exist, routine rollback by destructive `DROP TABLE` is not acceptable.

Production correction should use forward migrations.

### Decision

Migration 001 is **development-reversible, production-forward-oriented**.

---

## 28. Legacy Coexistence Contract

Migration 001 must not assume the legacy G1–G13 schema is the new canonical model.

The new vertical-slice tables should coexist safely with legacy tables during transformation.

Rules:

- do not rename/delete legacy tables in Migration 001;
- do not attach new canonical scientific semantics to old global gate statuses;
- do not copy legacy PASS/FAIL gates into new tables;
- do not restart or depend on the failed legacy G6–G9 service;
- future data adaptation happens explicitly after inventory/mapping.

This preserves the migration principle:

> **Preserve evidence assets; replace orchestration complexity; build continuous intelligence around them.**

## 30. Telegram Fixture Boundary

Migration 001 does not need to send Telegram messages.

The fixture only needs enough canonical data for a later Telegram projection test:

```text
ChangeEvent
+ project
+ GapCandidate
+ evidence counts
+ CoverageContext
```

Telegram remains a projection of canonical state, not a separate fixture truth store.

---

## 31. Migration 001 Acceptance Criteria

Migration 001 design is ready for implementation when:

1. all 21 canonical tables map directly to the accepted DDL contract;
2. creation order resolves all FK dependencies cleanly;
3. no domain-specific schema branch exists;
4. fixture A and B use the same schema and SQL shape;
5. each fixture contains supporting and challenging/alternative evidence;
6. GapCandidate evidence can traverse to SourceRecord;
7. machine Assessment is separate from HumanDecision;
8. CoverageContext is independently queryable;
9. fixture data is unmistakably synthetic;
10. verification is read-only and deterministic;
11. development rollback is defined;
12. production evolution is forward-oriented;
13. Migration 001 does not modify legacy orchestration tables/services;
14. no global research gate is introduced.
